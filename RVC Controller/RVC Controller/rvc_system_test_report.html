1. 테스트 목적

RVC(Robot Vacuum Cleaner) Controller의 FSM(Finite State Machine) 로직이 설계 스펙(DFD/FSM 다이어그램)대로 동작하는지, 시스템 수준(System Testing)에서 검증한다.

  • 빌드: Visual Studio 2022, MSVC, /utf-8 옵션 적용
  • 대상 플랫폼: x64 / Debug
  • 산출물: rvc_system_test_report-Results.xml (CUnit이 직접 생성하는 공식 결과 파일), 본 문서는 그 결과를 사람이 보기 좋게 정리한 리포트

3. 테스트 방법론 — Unit Test가 아닌 System Test인 이유

이 프로젝트는 두 종류의 테스트 파일을 가지고 있다.

  • test_rvc_controller.c — 유닛 테스트. 내부 함수(controller_step())를 직접 호출해서 한 tick의 상태 전이 로직만 떼어내 검증한다. (현재는 controller_step()이 controller() 내부로 통합되면서 더 이상 컴파일되지 않아 미사용 상태)
  • test_rvc_system.c — 시스템 테스트. 아래 방식으로, 내부 구현을 전혀 모르는 상태에서 외부에서 관찰 가능한 입출력만으로 검증한다.

시스템 테스트로 분류하는 근거:

  1. 실제 진입점을 그대로 사용한다. 내부 함수를 직접 부르지 않고, main()이 실제로 호출하는 것과 동일한 controller(initial_state)를 그대로 실행한다.
  2. 실시간 tick 타이밍을 그대로 사용한다. controller()는 clock() 기반으로 약 1초에 한 번씩 판단하는 while(1) 무한루프다. 이 루프를 건너뛰지 않고, 별도 스레드로 실제 실행시킨 뒤 일정 시간 기다렸다가 종료시키는 방식으로 테스트한다 (begin_run / end_run).
  3. 블랙박스 검증. 내부 상태 변수(last_state, tick_5 등)를 직접 읽지 않고, 시스템이 실제로 출력하는 모터/청소기 명령(FORWARD, LEFT, RIGHT, BACKWARD, ON, OFF, POWER UP)만으로 동작을 판정한다.
  4. 센서 입력도 공식 경로로 주입한다. 센서값은 front_sensor_input 등 전역 변수를 통해 주입하는데, 이는 소스에 "테스트에서는 실행 전에 센서 입력값을 바꿀 수 있다"라고 명시된 공식 테스트 인터페이스다.

4. 테스트 케이스 설계

테스트 이름의 [F L R D]는 Front/Left/Right(장애물) · Dust(먼지) 센서 입력값이다 (0=미감지, 1=감지). 쉼표로 여러 개가 이어지면, 각 묶음을 1tick씩 순서대로 입력했다는 뜻이며, 실행 도중 센서값이 바뀌는 시나리오를 나타낸다. 모든 테스트는 항상 MOVE_FORWARD(실제 main()과 동일한 시작 상태)에서 출발한다.

설계 원칙: ① 전진 중 F/L/R 8가지 조합 전수 테스트, ② 후진 진입 후의 좌/우회전·유지, ③ 회전/파워업이 4tick을 다 채우고 정상 복귀하는 경우, ④ 회전/파워업이 끝나기 전에 중단되는 경우, ⑤ 여러 상태를 길게 이어 붙인 종합 시나리오.
